# Bounded encrypted file acquisition

`FileAcquisitionStore` is an isolated Windows-native acquisition primitive for explicit forensic collection. It accepts only a relative source path under an explicitly configured absolute collection root, holds a read-only file handle for the capture, resolves the opened handle's normalized final path, and records volume/file identity. It refuses reparse-point roots and targets, alternate data streams, traversal, directories, missing configuration, and targets whose final path is outside the configured root. The root handle's path and identity and the source handle's path, identity, size, and last-write time are checked again after reading.

The source is opened with read access and sharing that allows readers only, blocking new write/delete opens while this handle is held. Windows does not revoke existing writable handles. Therefore this code uses held-handle identity and before/after metadata checks to detect many concurrent changes; it does not claim an atomic filesystem snapshot. A metadata or identity change yields a `partial` capture. The source is never written, moved, quarantined, or executed.

Each bounded chunk is encrypted independently with AES-256-GCM through Windows CNG. A fresh system-generated nonce, capture id, chunk sequence, and byte offset are authenticated; a per-capture SHA-256 covers the captured bytes. The manifest is HMAC-authenticated with the same key. The chunk is written to an encrypted `.part` file, flushed, atomically renamed, and then the manifest is atomically replaced and flushed. There are no plaintext files or plaintext temporary files. Plaintext exists only in bounded process memory and is cleared after use. The integrated action loads or creates a random key protected by the current Windows account's DPAPI at `acquisition-key.dpapi` inside the explicitly configured store root; unreadable keys fail closed and are never rotated automatically. For a newly created store directory, the implementation installs a protected DACL granting full access only to the current process token owner and SYSTEM. For a pre-existing directory and key, it inspects the DACL and accepts only an owner-matched, two-principal restricted ACL; otherwise it fails closed with instructions to configure a dedicated protected store. It never replaces an existing DACL or recursively changes existing child permissions. The acquisition store rechecks the protected DACL and holds the root directory against delete/rename while writing. New artifacts inherit the protected store ACL. Key rotation requires an explicit retention/rewrap policy.

Capture ids are bounded filename-safe idempotency keys. A committed `complete` or `truncated` capture returns the original result for an identical source identity and refuses reuse for another source. A `partial` capture can resume only if its final path, source identity, size, last-write time, root identity, byte cap, and chunk size still match. Resume authenticates and decrypts the already committed chunks to rebuild the running hash, then continues at the committed byte offset. If a crash happens after a chunk commit but before its manifest update, the next attempt adopts that orphan only after authenticating it and matching its plaintext to the same held source bytes at the expected offset. Sequence/accounting mismatch, authentication failure, or source mismatch stops acquisition and retains the evidence for inspection.

Manifest states are:

- `complete`: all bytes present at admission were acquired and the final held-handle checks passed; SHA-256 scope is `complete_source`.
- `truncated`: the caller/configured cap ended acquisition before end of file; the hash scope is `captured_prefix` and this is not a complete-file hash.
- `partial`: a short read, changing source/root, or recoverable interruption left a resumable prefix; hash scope, when available, is `captured_prefix`.
- `refused`: policy or identity admission failed before acquisition. These refusals do not create source data or a manifest.
- `failed`: storage, manifest, cryptographic, or consistency processing failed. If a durable partial manifest exists, the returned result reports `partial` so recovery remains visible.

Defaults cap each capture at 256 MiB and each chunk at 1 MiB; configuration permits at most 4 GiB per capture and 16 MiB per chunk. A single operation is serialized per store instance. The current class protects in-process calls with a mutex; it does not provide a cross-process store lock. Deploy one writer per configured store directory. Disk space is not reserved in advance: storage exhaustion can leave an explicitly reported partial capture. The manifest is plaintext metadata; sensitive path confidentiality therefore depends on access controls for the configured store.

## Integration and qualification status

`ACQUIRE_FILE` is an analyst-approved schema-1 action with exact target `{path, capture_id, maximum_bytes}`. The agent resolves `path` only beneath `--file-collection-root`; output is confined to the separately configured `--forensic-store-root`. A wire request may ask for at most 4 GiB, while this Windows build applies a 256 MiB per-capture local cap. The action sends only capture id, state, byte count, and captured-prefix/full-file SHA-256 in the durable command result. Encrypted content stays on the endpoint; Manager has no chunk-download protocol yet. On restart, only an `executing` `ACQUIRE_FILE` command is eligible for recovery. Automatic recovery requires an authenticated manifest bound to the same durable command id and correlation id, capture id, exact requested relative path and requested byte limit (as well as the effective cap and chunk size), and a still-matching normalized source path, file identity, size, last-write time, and collection-root identity. A matching terminal manifest is committed as the result; a matching partial capture may resume. Missing, unauthenticated, mismatched, or keyless evidence produces `indeterminate` and is never recreated. Other executing actions remain `indeterminate` and are not replayed. The DPAPI key is never provisioned during restart recovery. A new separately authorized command may resume a matching partial capture only if it preserves the original correlation id, capture id, exact path and byte limit, and all source/store identity checks pass. The Linux agent does not implement `ACQUIRE_FILE` and rejects it as an unsupported action.

The source is part of `officer-response` and routes through the existing durable command inbox/result outbox. This component deliberately does not reuse `DurableJournal` as a blob store: the journal encrypts bounded records but exposes no transactional large-object/chunk API. The integration and recovery path have received static review only. They have not been compiled, tested, or exercised on Windows; restart crash points, disk-full, DPAPI account migration, ACL setup, filesystem races, and VM qualification remain outstanding.
