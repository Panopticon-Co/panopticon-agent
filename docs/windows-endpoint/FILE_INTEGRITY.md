# Configured-root file integrity sensor

`FileIntegritySensor` adds a native Windows baseline and change source for directories selected explicitly by configuration. An empty root list leaves the source disabled. It does not infer roots from drive enumeration, monitor the whole machine, or change files. The current admission contract accepts absolute drive paths such as `C:\\ProgramData\\Contoso`; UNC paths are rejected. Current coverage is limited to direct children of each configured root. Nested directories are deliberately not traversed, so configure each directory that needs monitoring as its own root.

The sensor checks each configured root path component by opening it with `FILE_FLAG_OPEN_REPARSE_POINT`, then retains the root volume/file identity and normalized final path. Before reading candidate metadata or contents, it verifies the candidate handle's normalized final path is a direct child of the retained root handle's final path and rechecks that the root handle still has the admitted identity and path. It repeats these checks before each bounded content read and after hashing. Candidate file handles omit delete sharing while open, and final reparse points are opened with `FILE_FLAG_OPEN_REPARSE_POINT`; a refusal or identity/path change produces a degraded observation with no hash. Per-file observations include attributes, size, last-write time, volume/file identity, and SHA-256 when the entire file fits the per-file and remaining read budgets. A file whose identity, size, or last-write time changes during hashing gets no complete hash. Directories and files above the byte limit still produce bounded metadata. Baseline rows are individually submitted, so the baseline is durable in accepted pieces but is not an atomic filesystem snapshot.

The watcher opens the configured root with `ReadDirectoryChangesW`, `FILE_FLAG_OVERLAPPED`, and non-recursive notifications for names, attributes, size, last write, and creation. Native notification buffers are capped at 64 KiB. Each native buffer is parsed with bounds checks and capped candidate count. Rename old/new names are preserved as independent facts; pairing is explicitly uncertain. Current object metadata is sampled after notification delivery, so it may reflect a later state than the change itself. The source reports no actor and does not claim process attribution, execution, injection, prevention, or full filesystem coverage.

Every source record uses `make_record` to obtain the canonical immutable record body and `commit` to atomically accept that body with the next source checkpoint. The worker retries the same body after refusal and does not advance its sequence until `commit` succeeds. The host integration should adapt these callbacks to `DurableJournal::source_checkpoint`, the existing canonical record factory, and `DurableJournal::append_checkpointed`; it should never treat a volatile queue handoff as acceptance. A root checkpoint uses a fixed-length SHA-256-derived source key from the normalized configured path and contains a versioned format marker, root identity, and accepted sequence. On load, format/version and root identity are checked before the sequence is interpreted; an identity mismatch produces an explicit gap and starts a new sequence for the new root identity.

On restart with a prior checkpoint, the worker accepts a source-gap record before rebuilding a fresh baseline. A native buffer overflow, malformed notification buffer, or candidate-count truncation also produces a gap record with unknown loss and triggers a bounded rescan where possible. These records make uncertainty visible; they cannot reconstruct changes that Windows no longer retains. A process crash, shutdown with a pending record, unavailable root, native call failure, and callback refusal remain visible through worker state and counters. Lifetime counters are local to the current sensor object; abrupt-exit unaccepted counts are unknown.

Default application bounds are eight roots, 10,000 baseline candidates per scan, 256 candidates per native buffer, 2,048 UTF-8 bytes per relative path, 16 MiB per-file hash reads, 256 MiB hash reads per baseline or notification batch, and at most 64 KiB native bytes per root. Baseline stack, candidate vectors, buffers, and hashes are bounded by those limits. Win32 filesystem calls, hashing time, callbacks, and `stop()` joins do not have hard deadlines. The sensor skips direct-child reparse points and rejects notification names containing path separators; it never descends through a directory or reads contents from a candidate whose final path is outside the retained configured-root handle. One overlapped request is outstanding per root; shutdown cancels it and waits for terminal completion before releasing the event, operation, or backing buffer. Directory/file name enumeration uses Win32 path APIs, so its names are treated only as candidate hints until the held-handle final-path checks pass.

## Integration and remaining validation

1. Integrated: `src/collectors/file_integrity.cpp` is built into `officer-collectors`, with `bcrypt` linked for SHA-256.
2. Construct the sensor only with the explicit configured root list; preserve an empty list as disabled.
3. Supply callbacks that load a source checkpoint, create the canonical record, and call `append_checkpointed` before reporting acceptance.
4. Expose `snapshot()` through the existing source health/reporting path. Keep `full_file_coverage_verified` false and retain all gap/refusal state.
5. Include a Windows integration phase for root admission, reparse handling, baseline bounds, file identity/hash stability, notification parsing, overflow/restart gap records, durable refusal/retry, and stop behavior. The integrated Windows main executable compiles. This subsystem has not yet been exercised at runtime; tests are deferred to the final integration phase.
