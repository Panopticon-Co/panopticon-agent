# Configured-root file integrity sensor

`FileIntegritySensor` adds a native Windows baseline and change source for directories selected explicitly by configuration. An empty root list leaves the source disabled. It does not infer roots from drive enumeration, monitor the whole machine, or change files. The current admission contract accepts absolute drive paths such as `C:\\ProgramData\\Contoso`; UNC paths are rejected. Recursive baseline and subtree notifications are enabled by default for each explicit root. Callers can set `FileIntegrityLimits::recursive=false` to retain direct-child behavior.

The sensor checks each configured root path component by opening it with `FILE_FLAG_OPEN_REPARSE_POINT`, then retains the root volume/file identity and normalized final path. Before reading candidate metadata or contents, it verifies the candidate handle's normalized final path is a descendant of the retained root handle's final path (or a direct child when recursion is disabled) and rechecks that the root handle still has the admitted identity and path. It repeats these checks before each bounded content read and after hashing. Candidate file handles omit delete sharing while open, and final reparse points are opened with `FILE_FLAG_OPEN_REPARSE_POINT`; a refusal or identity/path change produces a degraded observation with no hash. Baseline traversal is iterative, tracks directory volume/file identities, and skips reparse points and repeated directory identities instead of following them. Depth, unique-directory, total-entry and relative-path bounds produce explicit durable gap/refusal records. Per-file observations include attributes, size, last-write time, volume/file identity, and SHA-256 when the entire file fits the per-file and remaining read budgets. A file whose identity, size, or last-write time changes during hashing gets no complete hash. Directories and files above the byte limit still produce bounded metadata. Baseline rows are individually submitted, so the baseline is durable in accepted pieces but is not an atomic filesystem snapshot.

The watcher opens the configured root with `ReadDirectoryChangesW`, `FILE_FLAG_OVERLAPPED`, and subtree notifications when recursion is enabled. Native notification buffers are capped at 64 KiB. Each native buffer is parsed with bounds checks and capped candidate count; notification paths are validated segment-by-segment as bounded relative paths. Rename old/new names are preserved as independent facts; pairing is explicitly uncertain. Current object metadata is sampled after notification delivery, so it may reflect a later state than the change itself. The source reports no actor and does not claim process attribution, execution, injection, prevention, or full filesystem coverage.

Every source record uses `make_record` to obtain the canonical immutable record body and `commit` to atomically accept that body with the next source checkpoint. The worker retries the same body after refusal and does not advance its sequence until `commit` succeeds. The host integration adapts these callbacks to `DurableJournal::source_checkpoint`, the canonical record factory, and `DurableJournal::append_checkpointed`; it does not treat a volatile queue handoff as acceptance. A root checkpoint uses a fixed-length SHA-256-derived source key from the normalized configured path and contains a versioned format marker, root identity, accepted sequence, and coverage scope including recursion and the traversal/hash bounds. A legacy checkpoint without scope metadata or a changed scope produces a durable coverage-scope gap before the baseline. Baseline begin, candidate/skip/gap records and a terminal manifest share the ordered checkpoint stream. Missing terminal manifests indicate that the baseline was interrupted or bounded before completion; per-row commit does not make the filesystem snapshot atomic.

On restart with a prior checkpoint, the worker accepts a source-gap record before rebuilding a fresh baseline. A native buffer overflow, malformed notification buffer, or candidate-count truncation also produces a gap record with unknown loss and triggers a bounded rescan where possible. These records make uncertainty visible; they cannot reconstruct changes that Windows no longer retains. A process crash, shutdown with a pending record, unavailable root, native call failure, and callback refusal remain visible through worker state and counters. Lifetime counters are local to the current sensor object; abrupt-exit unaccepted counts are unknown.

Default application bounds are eight roots, 10,000 baseline entries per scan, 2,048 visited directories, depth 16, 256 candidates per native buffer, 2,048 UTF-8 bytes per relative path, 16 MiB per-file hash reads, 256 MiB hash reads per baseline or notification batch, and at most 64 KiB native bytes per root. These are application bounds; Win32 may perform internal work before returning. Baseline stack, identity set, candidate vectors, buffers, and hashes are bounded by those limits. Win32 filesystem calls, hashing time, callbacks, and `stop()` joins do not have hard deadlines. Reparse points and directory identity duplicates/aliases are reported as skipped gaps; depth or directory/entry limit hits report the unobserved remainder. Root identity/path changes produce a root-scoped loss gap and blind health. Overflow, zero-byte notification completion, malformed buffers, restart, and coverage-scope changes are durably recorded and trigger bounded rescans where possible. Such rescans are not atomic and do not recover exact missed changes. One overlapped request is outstanding per root; shutdown cancels it and waits for terminal completion before releasing the event, operation, or backing buffer. Directory/file name enumeration uses Win32 path APIs, so names are candidate hints until held-handle final-path checks pass.

## Integration and remaining validation

1. Integrated: `src/collectors/file_integrity.cpp` is built into `officer-collectors`, with `bcrypt` linked for SHA-256.
2. Construct the sensor only with the explicit configured root list; preserve an empty list as disabled.
3. Supply callbacks that load a source checkpoint, create the canonical record, and call `append_checkpointed` before reporting acceptance.
4. Expose `snapshot()` through the existing source health/reporting path. Keep `full_file_coverage_verified` false and retain all gap/refusal state.
5. Include a Windows integration phase for root admission, recursive depth/identity/reparse handling, baseline bounds and terminal manifest behavior, file identity/hash stability, nested notification parsing, overflow/restart/scope/root-change gap records, durable refusal/retry, and stop behavior. This recursive wave has not been built, tested, or exercised at runtime; validation is deferred to final integration.
