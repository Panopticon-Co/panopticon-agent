# Native thread inventory

The endpoint independently samples one Windows Toolhelp thread snapshot, then opens each reported TID with THREAD_QUERY_LIMITED_INFORMATION and SYNCHRONIZE. Descriptors and later held-object queries remain separate because a TID can be reused between enumeration and OpenThread. No thread manipulation or privilege enablement is performed.

Held-object queries retain GetThreadId, GetThreadTimes creation/kernel/user 100 ns FILETIME values, GetProcessIdOfThread owner PID, GetThreadPriority raw relative priority, QueryThreadCycleTime raw cycles and a zero-timeout termination observation. Undefined exit time is always null. CPU cycles are not converted to elapsed time. The queries describe one held object with non-atomic fields; they do not establish present liveness after capture.

A native exact thread reference requires host identity, native boot identity, actual held TID and nonzero creation FILETIME. `thread_` identities use SHA-256 over the `windows-thread-instance-v1` prefix plus length-prefixed UTF-8 host, boot, decimal TID and decimal creation token. Missing boot or creation evidence leaves the entity null. This OS-specific body is additive to endpoint envelope 1.0. An owner PID is a report, never a process-instance join; owner process reference stays null. Start addresses are not queried.

The collector runs independently every five minutes through the existing native-state workers. Begin, bounded pages and an ordered manifest enter the encrypted FULL/WAL journal. Each canonical record is held unchanged until acceptance. Abrupt exit before acceptance can lose the volatile pending record; accepted pages remain recoverable, and a missing final manifest means an incomplete capture. Native fields, query failures, refusal/cancellation/bound state and record-bound capture freshness remain visible. After six minutes a committed snapshot becomes blind. C remains partial: handles, interactions, thread creation/exit continuity, thread impersonation, start addresses, remote-thread/injection attribution and protected-process coverage are unqualified or absent.

Default application bounds are 64 entries/page, 512 KiB/page, 16,384 total entries, 1,024 pages and a 60 second soft between-call budget. Toolhelp snapshot allocation and Windows API calls have no hard allocation cap/deadline; native worker isolation, storm/soak and resource qualification remain open. The current shared Pager reserves metadata space and can retain a row-copy refusal rather than silently dropping an oversized row.

Native host tests exercise the owned live thread against independent Windows API calls, unknown boot identity, total admission bounds, rejected pages, cancellation and invalid limits. Final consolidated builds and dedicated VM capture evidence are recorded in VALIDATION.md. Component evidence is separate from recovered runtime evidence; neither qualifies the whole thread surface.

API references: [GetThreadTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadtimes), [GetProcessIdOfThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocessidofthread), [Thread32First](https://learn.microsoft.com/en-us/windows/win32/api/tlhelp32/nf-tlhelp32-thread32first).
